# Object storage (R2 / S3-compatible)

Apps depend on `ObjectStorage` in `@khepree/storage`, not on a vendor SDK in UI code. Production uses the S3 adapter against R2-compatible endpoints. Development may use `MockObjectStorage` when credentials are omitted. Production and staging **must not** use the mock: both buckets are required (`validateRuntimeEnv()`).

## Buckets

| Logical bucket | Env | Hostname (production) | Contents |
|----------------|-----|------------------------|----------|
| public | `R2_BUCKET_PUBLIC` | cdn.khepree.com (`R2_PUBLIC_BASE_URL`) | Marketing images, public screenshots |
| private | `R2_BUCKET_PRIVATE` | download.khepree.com (signed URLs, not a public listing) | Installers, CMS bodies, protected files |

Private **never** falls back to public. Object keys are minted server-side (`createObjectKey`). Client filenames are not trusted.

Use **separate buckets or prefixes** per environment (`docs/ENVIRONMENTS.md`).

## Public domain

Point `cdn.khepree.com` (or your public asset host) at the public bucket’s public access / CDN. `R2_PUBLIC_BASE_URL` must be that HTTPS origin. SVG uploads to the public bucket are blocked.

## Private / downloads

`download.khepree.com` should not list the bucket. Browsers receive short-lived presigned GET URLs from `DownloadService` after authorization. Product-scoped objects (`media.context = product:<id>`) require an entitlement.

CMS bodies use private keys such as `prv/content/{entryId}/{locale}/v{n}.md`. Failed DB writes can leave orphan objects; cleanup is operational.

## CORS

Browser **uploads** use presigned PUT. If admin/account upload from a browser origin, set CORS on the **private** (and public, if used) buckets to allow:

- Origins: the admin and account HTTPS origins for that environment (not `*`)
- Methods: `PUT`, `GET`, `HEAD`
- Headers: `Content-Type` and any checksum headers you send

Server-side Node uploads do not need CORS. If all uploads stay server-side, CORS can stay closed.

Presigned **downloads** opened as top-level navigations typically do not need CORS. Fetching a private object from JavaScript on another origin does.

## Lifecycle and retention

Configure on the bucket (not in app code):

- **Incomplete multipart uploads** — abort after a few days.
- **Non-current versions** (if versioning is on) — expire according to backup policy.
- **Public marketing assets** — keep while referenced from CMS; unused objects can be expired only after you confirm no `media_assets` row points at them.
- **Private installers** — retain at least as long as customers may download that release; align with backup of `media_assets` metadata in Postgres.

Lifecycle rules that delete live objects while Postgres still references them will 404 entitled downloads. Coordinate deletes with catalog/admin.

## Backup

Object storage is not a substitute for database backups. Versioning + cross-bucket replication (or vendor object lock) is the usual approach. Restore drill: copy a known object back and complete a download through the app with a test entitlement.
